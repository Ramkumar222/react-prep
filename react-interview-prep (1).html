Section 01
Essential JavaScript
Prerequisites

Before React makes sense, these JS concepts must be second nature. React is built on top of all of them.

Definition
A closure is a function that retains access to its lexical scope — the variables declared in the environment where it was created — even after that outer function has finished executing and returned. In JavaScript, every time you create a function inside another function, you create a closure. The inner function carries a "backpack" of references to the outer variables, not copies of their values.
Model Interview Answer
A closure is formed when an inner function references a variable from an outer function's scope. Even after the outer function returns, the inner function keeps a live reference — not a snapshot — to those variables. This is fundamental to React because every hook callback (useEffect, useCallback, event handlers) is a closure that closes over the component's current state and props values at the time it was created.

Why Closures Matter in React

React hooks are entirely built on closure mechanics. When you call useState, React gives you a getter (count) and a setter (setCount). The setter is a closure that knows which state slot to update. When your event handler captures count, it forms a closure over that particular render's value.

Three Key React Use-Cases

1
useState internals
Each render's setter function closes over the correct memory slot in React's internal fiber.
2
useEffect cleanup
The cleanup function closes over the subscription/timer reference created during setup, so it can cancel the right one.
3
Custom hooks
All custom hook logic is a series of closures sharing common outer state variables.
The Stale Closure Problem
When a useEffect with an empty dependency array [] captures a state variable, it captures the initial value (e.g. count = 0) and never sees updates. This is the most common React bug. Fix it by:
• Adding the variable to the dependency array
• Using the functional updater: setCount(prev => prev + 1)
• Using useRef to hold a mutable reference
CLOSURE — EXAMPLE 1: COUNTER FACTORY
// makeCounter is a closure factory
function makeCounter(start = 0) {
  let count = start; // outer variable — "captured"

  return {
    increment: () => ++count,
    decrement: () => --count,
    reset:     () => { count = start; },
    getCount:  () => count,
  };
}

const c1 = makeCounter(5);
c1.increment(); // 6
c1.increment(); // 7
c1.reset();     // back to 5

// Each call to makeCounter creates a NEW closure
// c1 and c2 have completely separate 'count' vars
const c2 = makeCounter(100);
c2.getCount(); // 100 — independent of c1
CLOSURE — EXAMPLE 2: STALE CLOSURE BUG
function Timer() {
  const [count, setCount] = useState(0);

  // ❌ BUG: count is always 0 inside here
  //    because the closure captured the initial render
  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1); // always 0 + 1 = 1
    }, 1000);
    return () => clearInterval(id);
  }, []); // empty deps → stale closure!

  // ✅ FIX: functional updater avoids closure issue
  useEffect(() => {
    const id = setInterval(() => {
      setCount(prev => prev + 1); // ✓ always fresh
    }, 1000);
    return () => clearInterval(id);
  }, []);

  return <p>{count}</p>;
}
Memory Aid
Think of a closure as a function + its backpack. The backpack contains live references to outer variables. Every function in JavaScript automatically carries this backpack. The danger comes when the backpack is packed at creation time but you forget its contents can become stale.
Definition
Array methods like .map(), .filter(), and .reduce() are higher-order functions — they accept a callback function and return a new array (or value) without modifying the original. In React, this immutability is critical: React detects changes by reference equality, so mutating an array directly will not trigger a re-render.
Model Interview Answer
In React, all state updates must be immutable. Array methods like .map(), .filter(), and spread operator return new arrays instead of mutating the existing one. This lets React detect the change via reference comparison (oldArray !== newArray) and schedule a re-render. Mutating state directly (e.g. arr.push()) produces the same reference, so React sees no change and won't re-render.

.map() — Transform Every Item

.map(callback) iterates over every element, passes it to the callback, and builds a new array from the return values. The original array is untouched. Length stays the same. In React, this is used to render lists of JSX elements and to update a single item inside a state array.

  • Input: Array of N items
  • Output: New array of N items (transformed)
  • Use in React: Render lists, update one item by id
.MAP() — 3 REACT PATTERNS
// 1. Render a list
const users = [{id:1,name:'Alice'},{id:2,name:'Bob'}];
return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>;

// 2. Update one item immutably
setTodos(todos.map(t =>
  t.id === targetId
    ? { ...t, completed: !t.completed } // new obj
    : t                                      // unchanged
));

// 3. Transform API data before display
const prices = products.map(p => ({
  ...p,
  displayPrice: `$${p.price.toFixed(2)}`
}));

.filter() — Keep Matching Items

.filter(callback) builds a new array containing only the elements for which the callback returns true. Length may shrink. The original array is untouched.

.FILTER() — 3 REACT PATTERNS
// 1. Delete item from state
setUsers(users.filter(u => u.id !== deletedId));

// 2. Search/filter list
const filtered = items.filter(i =>
  i.name.toLowerCase().includes(query.toLowerCase())
);

// 3. Show only active items
const activeTodos = todos.filter(t => !t.completed);
const doneTodos   = todos.filter(t =>  t.completed);

.reduce() — Accumulate to Any Value

.reduce(callback, initialValue) iterates the array, maintaining a running "accumulator" that your callback updates each step. It can produce any type: a number, string, object, or even another array. It is the most powerful but most misunderstood of the three.

.REDUCE() — 4 REACT PATTERNS
// 1. Sum cart total
const total = cart.reduce(
  (acc, item) => acc + item.price * item.qty, 0
);

// 2. Group items by category
const grouped = products.reduce((acc, p) => {
  const key = p.category;
  return { ...acc, [key]: [...(acc[key] ?? []), p] };
}, {});
// { Electronics: [...], Clothing: [...] }

// 3. Convert array to lookup map
const byId = users.reduce((acc, u) => {
  acc[u.id] = u;
  return acc;
}, {});
// O(1) lookup: byId[42] instead of .find()

// 4. Flatten nested arrays
const flat = nested.reduce(
  (acc, arr) => [...acc, ...arr], []
);
Mutation vs Immutability
These are the wrong ways to update React state:
state.push(item) — mutates, same reference, no re-render
state[0].done = true — mutates nested object

Always return a new array from setState: use .map(), .filter(), spread, or .concat().
Definition
Destructuring is a concise ES6 syntax that lets you unpack values from arrays or properties from objects into distinct variables in a single statement. Spread (...) copies all remaining or enumerable properties into a new array/object. Rest (... in a parameter position) collects all remaining arguments into an array or object. Together these three patterns appear in virtually every React component.

Object Destructuring

Object destructuring extracts named properties into variables. The variable name must match the property key (or you provide a rename with :). You can set default values with =.

OBJECT DESTRUCTURING PATTERNS
// Basic destructuring from props
function Card({ title, description, onClick }) {
  return <div onClick={onClick}>{title}</div>;
}

// Rename: extract 'name' but call it 'username'
const { name: username } = user;

// Default value: use 'Guest' if name is undefined
const { name = 'Guest', age = 0 } = user;

// Rename + default combined
const { name: username = 'Guest' } = user;

// Nested destructuring
const { address: { city, zip } } = user;

// In useEffect dependency:
const { id, role } = currentUser;
useEffect(() => { fetchData(id); }, [id]);

Array Destructuring

Array destructuring extracts values by position. Variable names are chosen freely. This is exactly how React's useState hook works — it returns a two-element array [value, setter].

ARRAY DESTRUCTURING
// This IS array destructuring:
const [count, setCount] = useState(0);

// Skip elements with commas
const [, second, , fourth] = [1,2,3,4];

// Swap two variables elegantly
let a = 1, b = 2;
[a, b] = [b, a]; // a=2, b=1

// Custom hook pattern returns array
function useToggle(init = false) {
  const [on, setOn] = useState(init);
  return [on, () => setOn(v => !v)];
}
const [isOpen, toggleOpen] = useToggle();

Spread Operator (...)

Spread copies all enumerable own properties of an object (or elements of an array) into a new one. This is the primary tool for immutable state updates in React, because it produces a new object/array reference.

SPREAD FOR IMMUTABLE STATE UPDATES
// Object: copy all, override 'age'
setUser(prev => ({ ...prev, age: 25 }));

// Nested object update (must spread each level!)
setUser(prev => ({
  ...prev,
  address: { ...prev.address, city: 'Hyderabad' }
}));

// Array: add item at end
setItems(prev => [...prev, newItem]);

// Array: add item at beginning
setItems(prev => [newItem, ...prev]);

// Pass all props + override one
<Button {...baseProps} disabled={true} />

// Clone an array (same values, new reference)
const sorted = [...original].sort();

Rest Operator (...)

Rest collects everything that wasn't destructured into a new variable. In component props, this is the standard pattern for passing "extra" HTML attributes down to a DOM element.

REST OPERATOR IN COMPONENTS
// Extract known props, forward the rest
function Button({ label, variant = 'primary', ...htmlProps }) {
  return (
    <button
      className={`btn btn-${variant}`}
      {...htmlProps} // onClick, disabled, type, etc.
    >
      {label}
    </button>
  );
}

// Rest in function params
function logAll(first, ...rest) {
  console.log(first); // first arg
  console.log(rest);  // array of remaining
}
Definition
JavaScript is single-threaded but non-blocking. Asynchronous operations (network requests, timers, file reads) are offloaded to the browser's Web APIs. When they complete, their callback is placed in the event queue. The event loop continuously checks if the call stack is empty, and if so, moves the next callback from the queue onto the stack. A Promise is an object representing the eventual completion (or failure) of an async operation. async/await is syntactic sugar over Promises that makes asynchronous code read like synchronous code.
Model Interview Answer
JavaScript uses an event loop to handle asynchrony without blocking the main thread. A Promise has three states: pending, fulfilled, or rejected. async/await lets you write async code sequentially. In React, data fetching always lives inside useEffect (since components are pure render functions that must not produce side effects). You must handle three UI states: loading, data, and error.

Promises — Three States

pending
Initial state. The async operation is still in progress. Neither fulfilled nor rejected yet.
fulfilled
Operation succeeded. The .then() handler runs with the resolved value.
rejected
Operation failed. The .catch() handler runs (or the catch block in try/catch).

async / await

async marks a function as asynchronous — it always returns a Promise. await pauses execution inside that function only (the event loop is not blocked) until the Promise resolves, then resumes with the resolved value. Any rejected promise inside an async function throws and can be caught with try/catch.

Critical React Rule: You cannot make the useEffect callback itself async because async functions return a Promise, but React expects the return value to be either undefined or a cleanup function. Always define an inner async function and call it immediately.
PRODUCTION-GRADE DATA FETCHING
function useFetch(url) {
  const [state, setState] = useState({
    data:    null,
    loading: true,
    error:   null,
  });

  useEffect(() => {
    // Reset state when URL changes
    setState({ data: null, loading: true, error: null });

    // AbortController cancels in-flight request
    const ctrl = new AbortController();

    // Inner async function (can't make outer async)
    (async () => {
      try {
        const res = await fetch(url, { signal: ctrl.signal });

        // Always check HTTP status
        if (!res.ok) throw new Error(`HTTP ${res.status}`);

        const data = await res.json();
        setState({ data, loading: false, error: null });
      } catch (err) {
        // Ignore AbortError — it's intentional
        if (err.name !== 'AbortError') {
          setState({ data: null, loading: false, error: err });
        }
      }
    })();

    // Cleanup: abort if component unmounts
    return () => ctrl.abort();
  }, [url]);

  return state;
}

// Usage
function UserProfile({ id }) {
  const { data, loading, error } = useFetch(`/api/users/${id}`);
  if (loading) return <Spinner />;
  if (error)   return <Error msg={error.message} />;
  return <h1>{data.name}</h1>;
}
Definition — Scope
Scope determines where a variable is accessible. JavaScript has three scope types: Global (accessible everywhere), Function (accessible only inside a function — created by var), and Block (accessible only inside {} — created by let and const). Scopes nest: an inner scope can access outer scope variables but not vice versa. This nesting is what makes closures possible.
Definition — Hoisting
Hoisting is JavaScript's behaviour of moving declarations to the top of their scope during the compilation phase — before code executes. var declarations are hoisted and initialized to undefined. function declarations are hoisted entirely (including their body). let and const are hoisted to the top of their block but not initialized — accessing them before declaration throws a ReferenceError (this zone is called the Temporal Dead Zone).

var vs let vs const

Common Trap — const ≠ immutable: const prevents reassignment of the variable binding, not mutation of the value. You cannot do const x = 1; x = 2 but you can do const obj = {}; obj.name = 'Alice'. This is why React state still needs explicit setState calls even when declared with const.
SCOPE & HOISTING EXAMPLES
// Hoisting — var
console.log(x); // undefined (hoisted)
var x = 5;

// TDZ — let/const
console.log(y); // ReferenceError!
let y = 5;

// Block scope
if (true) {
  let blockVar = 'inside';
  var funcVar  = 'leaks!';
}
// console.log(blockVar); // ReferenceError
console.log(funcVar); // 'leaks!' — var escapes block

// Classic closure-in-loop bug (var)
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
  // Prints 3, 3, 3 — var is function-scoped
}

// Fix: use let (block scope per iteration)
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
  // Prints 0, 1, 2 ✓
}
Definition — Prototype Chain
Every JavaScript object has an internal [[Prototype]] link to another object (its prototype). When you access a property on an object and it's not found there, JavaScript automatically walks up the prototype chain until it finds it or reaches null. This is how method inheritance works: array methods like .map() live on Array.prototype, not on each individual array.
Definition — this
this refers to the execution context — the object that a function is called on. Its value is determined at call time, not at definition time (for regular functions). Arrow functions are the exception: they inherit this from their lexical (surrounding) scope at definition time and never have their own this. This is why React event handlers are almost always arrow functions.

this — 4 Binding Rules

1
Default binding
Regular function call: this is window (or undefined in strict mode).
2
Implicit binding
Method call — obj.method(): this is the object before the dot.
3
Explicit binding
.call(ctx), .apply(ctx), .bind(ctx): manually set this.
4
Arrow function
No own this — inherits from enclosing lexical scope. Cannot be re-bound.
React relevance: In class components, methods lose this when passed as event handlers — you must either .bind(this) in the constructor or use arrow function class fields. Function components with hooks avoid this problem entirely.
this BINDING EXAMPLES
const obj = {
  name: 'Alice',
  greetRegular: function() {
    return `Hello ${this.name}`; // 'this' = obj
  },
  greetArrow: () => {
    return `Hello ${this.name}`; // 'this' = outer (window)
  },
};

obj.greetRegular(); // 'Hello Alice' ✓
obj.greetArrow();   // 'Hello undefined' ✗

// Class component — this problem
class Toggle extends React.Component {
  constructor(props) {
    super(props);
    this.state = { on: false };
    // Must bind, or 'this' is undefined in handler
    this.handleClick = this.handleClick.bind(this);
  }
  handleClick() {
    this.setState(s => ({ on: !s.on }));
  }
}
// Function components have NO 'this' issues
Section 02
Core React Concepts
Theory & Architecture

Deep conceptual questions are asked at every level. Know the "why" not just the "how".

Definition — Virtual DOM
The Virtual DOM (VDOM) is a lightweight, in-memory JavaScript representation of the real browser DOM. It is a plain JavaScript object tree that mirrors the structure and properties of actual DOM nodes — but lives in JS memory, not in the browser. React maintains two virtual trees at any time: the current tree (what's on screen) and the work-in-progress tree (what the next render should produce).
Definition — Reconciliation
Reconciliation is the algorithm React uses to determine the minimal set of DOM operations needed to bring the real DOM in sync with the latest Virtual DOM. When state changes, React re-renders the component to produce a new VDOM tree, then diffs it against the previous one. This diff produces a list of "patches" (insertions, deletions, updates) that React then applies to the real DOM in a single efficient batch — the commit phase.
Model Interview Answer
The Virtual DOM exists because direct DOM manipulation is expensive — reading layout properties, inserting nodes, and re-painting all trigger browser reflows. React keeps a lightweight JS copy of the DOM. When state changes, it re-renders to a new virtual tree and uses its diffing algorithm to find only the changed nodes. It then batches those minimal real DOM updates together, reducing browser work. React 18 introduced the Concurrent renderer, which can interrupt, pause, and resume rendering to keep the UI responsive.

The Diffing Algorithm Rules

1
Different element type → full replacement
If a <div> is replaced by a <span>, React destroys the entire subtree and mounts a fresh one. All child state is lost.
2
Same element type → update props only
If the element type stays the same (e.g. still a <div>), React only updates the changed attributes/props. The DOM node itself is reused.
3
Lists use keys for identity
Without key, React assumes list items at the same index are the same node. With key, React can correctly match, move, insert, or delete items even when order changes.
Never use array index as key in dynamic lists!
If you add/remove items or reorder them, index keys cause React to associate wrong state with wrong components — leading to bugs like input values appearing in the wrong fields. Always use a stable, unique ID from your data.
Memory Aid
Think of reconciliation like a smart version control diff. Instead of replacing the entire file, git computes the minimal set of line changes. React does the same for the DOM tree: minimal patches, maximum reuse.
KEY PROP — CORRECT vs WRONG
// ❌ WRONG: index as key
{items.map((item, index) => (
  <li key={index}>
    <input defaultValue={item.name} />
  </li>
))}
// Insert at top → index 0 reassigned → wrong input
// values appear in wrong fields!

// ✅ CORRECT: stable unique id
{items.map(item => (
  <li key={item.id}>
    <input defaultValue={item.name} />
  </li>
))}
// React tracks each item by ID — always correct

// ✅ ALSO OK: key to force full remount
// Changing key destroys+recreates the component
// Useful for resetting form state on user change:
<UserProfile key={userId} id={userId} />
RENDER PHASES
// RENDER PHASE (pure, can be interrupted in React 18)
// 1. Component function runs
// 2. Returns new VDOM tree
// 3. React diffs with previous VDOM

// COMMIT PHASE (sync, not interruptible)
// 4. DOM mutations applied
// 5. useLayoutEffect runs
// 6. Browser paints screen
// 7. useEffect runs (async, after paint)

function App() {
  const [n, setN] = useState(0);

  // This runs in render phase — must be pure!
  const double = n * 2; // ✓ pure computation

  // Side effects go in useEffect (commit phase)
  useEffect(() => {
    document.title = `Count: ${n}`; // ✓ side effect
  }, [n]);

  return <button onClick={() => setN(n+1)}>{double}</button>;
}
Definition — State
State is a component's private, mutable data. It is owned by the component and managed via useState or useReducer. State is local — other components cannot directly read or write it. When state changes (via a setter), React schedules a re-render of that component and all of its descendants. State persists between renders of the same component instance but is reset when the component unmounts.
Definition — Props
Props (short for properties) are the mechanism by which a parent passes data and callbacks to a child. Props are read-only inside the child — a child must never mutate its props. They flow strictly downward (parent → child). When a parent re-renders with new prop values, the child receives them and re-renders too. Props can be any JavaScript value: strings, numbers, objects, arrays, or functions (callbacks).
Model Interview Answer
State is internal, mutable, owned by the component — like a component's private memory. Props are external, immutable, inherited from the parent — like function arguments. The key design principle is unidirectional data flow: data flows down via props, and events flow up via callback props. A child wanting to change shared data calls a callback prop which triggers a state update in the parent, which flows new props back down.

Lifting State Up

When two sibling components need to share state, move the state up to their closest common ancestor. The ancestor owns the state, passes the data down as props to both children, and passes setter callbacks down so children can request changes.

LIFTING STATE UP
// ❌ Wrong: two separate local states get out of sync
function Filter() { const [q,setQ] = useState(''); }
function Results() { const [q,setQ] = useState(''); }

// ✅ Correct: state lifted to parent, shared via props
function SearchPage() {
  const [query, setQuery] = useState(''); // lifted here
  return (
    <>
      <Filter query={query} onSearch={setQuery} />
      <Results query={query} />
    </>
  );
}

function Filter({ query, onSearch }) {
  return <input value={query}
                 onChange={e => onSearch(e.target.value)} />;
}

function Results({ query }) {
  return <p>Showing results for: {query}</p>;
}

Definition — Component Lifecycle
Every React component goes through three phases: Mount (added to the DOM for the first time), Update (re-rendered due to state/prop changes), and Unmount (removed from the DOM). In function components, all three phases are handled by useEffect through its setup function, dependency array, and cleanup return value respectively.
Definition — What Triggers a Re-render?
A React component re-renders when: (1) its own state changes via a setter; (2) its parent re-renders (and by default passes new prop references even if values are equal); (3) a Context it subscribes to changes its value; or (4) forceUpdate() is called (class components only). A re-render does NOT mean a DOM update — it means React runs the render function to produce a new VDOM, then checks if the DOM needs updating.

Function Component Lifecycle Phases

MOUNT — Component appears in DOM
The component function runs for the first time. All useEffect hooks with [] dependency fire once after the first paint. Good for: subscriptions, data fetching, event listener setup.
UPDATE — State or props change
Component function runs again with new state/props. useEffect hooks with matching deps in the array fire. The cleanup from the previous run fires first, then the new setup.
CLEANUP (between updates)
Before each re-run of a useEffect (and on unmount), the cleanup function (the function returned from the effect) runs. Used to cancel subscriptions, clear timers, abort fetches.
UNMOUNT — Component leaves DOM
The cleanup function of every useEffect runs one final time. Component state is destroyed. The next mount will start with fresh initial state.
LIFECYCLE MAPPED TO useEffect
function ChatRoom({ roomId }) {
  const [msgs, setMsgs] = useState([]);

  // MOUNT: empty [] → runs once after first render
  useEffect(() => {
    logAnalytics('page_view');
    return () => logAnalytics('page_leave'); // UNMOUNT
  }, []);

  // UPDATE: runs when roomId changes
  // also runs on first mount
  useEffect(() => {
    const socket = connectToRoom(roomId);
    socket.on('message', msg =>
      setMsgs(prev => [...prev, msg])
    );

    // CLEANUP: fires before next roomId change + unmount
    return () => socket.disconnect();
  }, [roomId]); // ← dep

  // EVERY render: no deps array
  useEffect(() => {
    document.title = `${msgs.length} messages`;
  });

  return <ul>{msgs.map(m => <li key={m.id}>{m.text}</li>)}</ul>;
}
Avoid missing dependencies! Eslint's exhaustive-deps rule catches missing deps. A missing dep usually causes a stale closure bug.
Definition — Controlled Component
A controlled component is a form element whose value is entirely driven by React state. The component's value prop is set to a state variable, and an onChange handler updates that state on every keystroke. React state is the single source of truth — the DOM input value always reflects what's in state. This gives you complete, instant control over the input value at all times.
Definition — Uncontrolled Component
An uncontrolled component lets the DOM itself be the source of truth for form input values. Instead of syncing state on every keystroke, you attach a ref and read ref.current.value only when needed (e.g. on form submit). The DOM manages the value internally. This is closer to how vanilla HTML forms work.

Controlled — When to Use

  • Instant validation — show errors as user types
  • Conditional UI — show/hide other fields based on value
  • Format on input — phone number masking, slug generation
  • Disable submit button until all fields are valid
  • Programmatic value reset — clear form on cancel

Uncontrolled — When to Use

  • File inputs — <input type="file"> can only be uncontrolled
  • Third-party DOM lib integration (e.g. rich text editors)
  • Simple forms where you only need the value on submit
  • Performance — avoid re-renders on every keystroke
React Hook Form uses an uncontrolled approach internally for performance, then validates on submit — giving you the best of both worlds.
CONTROLLED vs UNCONTROLLED
// ═══ CONTROLLED ═══
function ControlledForm() {
  const [email, setEmail] = useState('');
  const [error, setError] = useState('');

  const handleChange = (e) => {
    const val = e.target.value;
    setEmail(val);
    // Instant validation — possible only with controlled
    setError(val.includes('@') ? '' : 'Invalid email');
  };

  return (
    <div>
      <input value={email} onChange={handleChange} />
      {error && <span style={{color:'red'}}>{error}</span>}
    </div>
  );
}

// ═══ UNCONTROLLED ═══
function UncontrolledForm() {
  const emailRef = useRef(null);
  const fileRef  = useRef(null);

  const handleSubmit = (e) => {
    e.preventDefault();
    const email = emailRef.current.value;
    const file  = fileRef.current.files[0];
    uploadFile(email, file);
  };

  return (
    <form onSubmit={handleSubmit}>
      <input ref={emailRef} type="email" />
      <input ref={fileRef}  type="file" />
      <button>Submit</button>
    </form>
  );
}
Definition — JSX
JSX (JavaScript XML) is a syntax extension for JavaScript that looks like HTML but compiles to regular JavaScript function calls. <MyComponent prop="value" /> compiles to React.createElement(MyComponent, { prop: "value" }). JSX is not a template language — it is just syntactic sugar over function calls that produce React element objects. Babel or the TypeScript compiler transforms JSX before the code runs in the browser.
Definition — Component Types
React has two types of components: Function Components — plain JavaScript functions that accept props and return JSX. They use hooks for state and side effects. Class Components — ES6 classes extending React.Component with a required render() method. They have lifecycle methods (componentDidMount, componentDidUpdate, etc.) but no hooks. The React team now strongly recommends function components with hooks for all new code.

JSX Rules to Know

  • Must return a single root element (use <Fragment> or <></> to group without adding a DOM node)
  • All tags must be closed: <br /> not <br>
  • Use className instead of class, htmlFor instead of for
  • JavaScript expressions go inside {}
  • Component names must be capitalized — lowercase is treated as a DOM element
  • Style prop takes an object: style={{ color: 'red' }}
  • Event handlers use camelCase: onClick, onChange

Hooks Mastery

The most tested React topic. Know every hook's definition, purpose, timing, and common pitfalls.

The 2 Rules of Hooks (memorize these):
1. Only call hooks at the top level — never inside loops, conditions, or nested functions. React tracks hooks by their call order; breaking the order corrupts the internal hook linked-list.
2. Only call hooks inside React function components or custom hooks — not in class components, regular utility functions, or event handlers.
Definition — useState
useState(initialValue) declares a state variable inside a function component. It returns a tuple: [currentValue, setterFunction]. The setter triggers a re-render with the new value. React ensures that within a single event (like a click), multiple setState calls are batched into a single re-render (React 18 batches all updates, including those in async callbacks). The initial value is only used on the first render; all subsequent renders use the stored state.

How useState Works Internally

React maintains an ordered list of "state cells" per component instance. Each useState call occupies a cell by its position in the call order. This is why hooks must always be called in the same order — so React can match each hook call to its corresponding cell.

Functional Updater Form

When the new state depends on the previous state, always use the functional updater setState(prev => newValue). This guarantees you're working from the most recent state, not a potentially stale closure value.

Lazy Initialization

If the initial state is expensive to compute (e.g. parsing localStorage), pass a function to useState. React calls it only on the first render, not on every re-render.

useState — ALL PATTERNS
// Basic
const [count, setCount] = useState(0);

// Object state — always spread to update immutably
const [user, setUser] = useState({ name:'', age:0 });
setUser(prev => ({ ...prev, name: 'Alice' }));

// Functional updater — safe with batching/concurrency
setCount(prev => prev + 1); // ✓ always fresh

// Lazy initialization — expensive init runs ONCE
const [data, setData] = useState(() => {
  const saved = localStorage.getItem('data');
  return saved ? JSON.parse(saved) : [];
}); // function, not the result!

// Batching in React 18 — single re-render
const handleClick = () => {
  setCount(c => c + 1);  // batched together
  setName('Bob');        // batched together
  // Only ONE re-render happens ✓
};
Common useState Mistakes
1. Direct mutation: state.push(x) — same reference, no re-render. Always return a new array/object.
2. Reading stale state: Reading count right after setCount(count+1) in the same render still gives the old value. The update is queued, not immediate.
3. Object state missing spread: setState({ age: 25 }) replaces the entire object. You need setState(prev => ({...prev, age: 25})).
4. Unnecessary state: If a value can be derived from state or props, don't store it as state — compute it during render.
Mental Model
Think of useState as a sticky note on the wall for a component. React reads the note, shows the UI, and when you call the setter, it changes what's on the note and re-draws the UI. The note survives re-renders but disappears when the component unmounts.
Definition — useReducer
useReducer(reducer, initialState) is an alternative to useState for managing complex state logic. It takes a pure reducer function ((state, action) => newState) and an initial state, and returns [currentState, dispatch]. You update state by dispatching action objects (dispatch({ type: 'increment' })) rather than calling setters directly. The reducer centralizes all state transition logic in one pure, testable function.
Model Interview Answer
Use useReducer when: (1) state has multiple sub-values that are updated together; (2) the next state depends on the previous in complex ways; (3) state transitions have distinct names (action types) that help describe what happened; or (4) you want the state logic to be independently unit-testable (pure functions are trivial to test). Think of it as a mini-Redux inside a single component. For simple, independent state values, useState is simpler and sufficient.

Reducer Pattern Explained

A reducer is a pure function: given the current state and an action, it returns the next state. It must not mutate the old state, produce side effects, or depend on anything outside its arguments. This purity makes it predictable and testable in complete isolation from React.

Definition — useEffect
useEffect(setup, dependencies?) lets you synchronize a component with an external system (APIs, subscriptions, timers, browser APIs, third-party libraries). It runs the setup function after the browser has painted (asynchronously, post-commit). The optional dependency array controls when it re-runs: an empty array [] means run once on mount; an array with values means run whenever any of those values change; no array means run after every render. The setup function can return a cleanup function that runs before the next setup call and on unmount.

Dependency Array Rules

1
No array — runs every render
Effect runs after every single render. Rarely what you want — creates performance issues and potential infinite loops.
2
Empty array [] — mount only
Effect runs once after the first render. Cleanup runs once on unmount. Good for one-time setup.
3
[dep1, dep2] — conditional
Effect runs on mount AND whenever any listed dependency changes. React compares deps using Object.is() (shallow equality).
Object/function deps cause infinite loops! If you put an object or function (created inline) in deps, it's a new reference on every render. The effect runs → triggers a re-render → new reference → effect runs again. Fix: use useMemo / useCallback, or extract the value outside the component.
useEffect — ALL DEPENDENCY PATTERNS
// ❌ Runs after EVERY render — dangerous
useEffect(() => { doSomething(); });

// ✅ Run once: subscribe on mount, unsubscribe on unmount
useEffect(() => {
  const sub = store.subscribe(render);
  return () => sub.unsubscribe(); // cleanup
}, []);

// ✅ Re-run when userId changes
useEffect(() => {
  const ctrl = new AbortController();
  fetchUser(userId, ctrl.signal).then(setUser);
  return () => ctrl.abort(); // cancel prev request
}, [userId]);

// ⚠️  Object in deps — causes infinite loop!
useEffect(() => { doSomething(config); }, [config]);
// config = { theme: 'dark' } — new obj every render!

// ✅ Fix: depend on the primitive value
useEffect(() => { doSomething(config); }, [config.theme]);

// ✅ Fix: memoize the object
const stableConfig = useMemo(() => ({ theme }), [theme]);
useEffect(() => { doSomething(stableConfig); }, [stableConfig]);
Definition — useLayoutEffect
useLayoutEffect has the same signature as useEffect but fires synchronously after all DOM mutations and before the browser has a chance to paint. This means any state updates inside it are flushed synchronously and the browser never shows an intermediate visual state — preventing flicker. The trade-off is that it blocks the browser from painting until it completes, so it must be fast.

useEffect vs useLayoutEffect

Decision rule: Start with useEffect. If the user sees a visual "flash" or position jump, switch to useLayoutEffect. That flash is the signal that you need to read the DOM and update state before the browser shows the frame.
useLayoutEffect — TOOLTIP POSITIONING
function Tooltip({ anchor, children }) {
  const ref = useRef(null);
  const [pos, setPos] = useState({ top:0, left:0 });

  // useEffect: tooltip briefly appears at wrong position
  // useLayoutEffect: position computed before paint → no flicker
  useLayoutEffect(() => {
    if (!ref.current || !anchor) return;

    const anchorRect = anchor.getBoundingClientRect();
    const tipHeight  = ref.current.offsetHeight;
    const tipWidth   = ref.current.offsetWidth;

    setPos({
      top:  anchorRect.top - tipHeight - 8,
      left: anchorRect.left + (anchorRect.width - tipWidth) / 2,
    });
  }, [anchor]);

  return (
    <div
      ref={ref}
      style={{ position:'fixed', top:pos.top, left:pos.left }}
    >
      {children}
    </div>
  );
}
Definition — useRef
useRef(initialValue) returns a mutable ref object { current: initialValue } that persists for the full lifetime of the component. Unlike state, mutating ref.current does not trigger a re-render. useRef has two distinct use-cases: (1) accessing DOM nodes directly by attaching the ref object to a JSX element's ref prop, and (2) persisting any mutable value across renders without causing re-renders — like a component-scoped instance variable.

Two Distinct Uses of useRef

Use 1 — DOM Reference

When you pass a ref to a JSX element's ref prop, React sets ref.current to the underlying DOM node after mount and clears it on unmount. This gives you direct imperative access to DOM APIs: focus(), blur(), scrollIntoView(), getBoundingClientRect(), media controls, canvas context, etc.

Use 2 — Mutable Instance Variable

Think of it as a box that lives alongside the component for its entire lifetime. You can read and write ref.current freely — it doesn't affect rendering. Common uses: storing a timer ID so it can be cancelled later, storing the previous value of a prop, tracking whether a component is still mounted (to prevent state updates after unmount), or storing a value set during an event that needs to be read by an effect.

useRef vs useState: If you need to show a value in the UI, use useState. If you need to remember a value between renders but don't need the UI to reflect it, use useRef. Mutating ref.current is a side effect — do it inside event handlers or effects, not during rendering.
useRef — 5 REAL PATTERNS
// 1. Focus a DOM element
const inputRef = useRef(null);
const focusInput = () => inputRef.current?.focus();
<input ref={inputRef} />

// 2. Store interval ID without re-render
const timerRef = useRef(null);
const start = () => { timerRef.current = setInterval(tick, 1000); };
const stop  = () => clearInterval(timerRef.current);

// 3. usePrevious — track previous prop value
function usePrevious(value) {
  const prevRef = useRef();
  useEffect(() => { prevRef.current = value; }); // runs after render
  return prevRef.current; // returns PREVIOUS render's value
}

// 4. isMounted guard (prevent setState on unmounted)
const isMounted = useRef(false);
useEffect(() => {
  isMounted.current = true;
  return () => { isMounted.current = false; };
}, []);

// 5. Store latest callback without re-creating effect
const callbackRef = useRef(callback);
useEffect(() => { callbackRef.current = callback; });
useEffect(() => {
  const id = setInterval(() => callbackRef.current(), 1000);
  return () => clearInterval(id);
}, []); // never stale — reads through ref
Definition — useContext
useContext(Context) subscribes a component to a React context. It reads the current value from the nearest matching Provider above it in the component tree. When the Provider's value changes, React re-renders all consumers. Context solves prop drilling — the need to pass data through many intermediate components that don't need it themselves. It is ideal for truly "global" values: current user, theme, locale, feature flags.

Three-Step Context Pattern

1
Create the context
createContext(defaultValue) — the default is used when there's no matching Provider above in the tree.
2
Provide it high in the tree
Wrap the part of the tree that needs access with <Context.Provider value={...}>. The value can be anything: a primitive, an object, or a tuple of [state, setter].
3
Consume anywhere below
const value = useContext(MyContext) in any descendant component — no matter how deeply nested.
Context re-render warning: Every component that calls useContext will re-render whenever the context value changes — even if it only uses a small part of it. For objects, every property change triggers re-renders in all consumers. Split large contexts into smaller ones, or use useMemo to stabilize the value object.
useContext — AUTH PATTERN
// auth-context.js
const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);

  const login = async (email, pass) => {
    const u = await authAPI.login(email, pass);
    setUser(u);
  };
  const logout = () => setUser(null);

  // Memoize value to prevent unnecessary re-renders
  const value = useMemo(() => ({ user, login, logout }),
    [user]);

  return (
    <AuthContext.Provider value={value}>
      {children}
    </AuthContext.Provider>
  );
}

// Custom hook for clean consumption
export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth must be inside AuthProvider');
  return ctx;
}

// Usage anywhere in tree
function NavBar() {
  const { user, logout } = useAuth();
  return <span>Hi {user?.name} <button onClick={logout}>Logout</button></span>;
}
Definition — Custom Hooks
A custom hook is a JavaScript function whose name starts with use and that can call other hooks inside. They allow you to extract stateful logic out of a component and share it between multiple components without changing their structure. Unlike HOCs (Higher-Order Components) or render props, custom hooks don't add extra nodes to the component tree. Each component that calls a custom hook gets its own independent state and effects — they share the logic, not the state.
Model Interview Answer
Custom hooks let you abstract and reuse stateful behaviour. The key principle is that two components using the same custom hook share the logic but not the state — each has its own independent state. This is the React equivalent of creating a utility function for pure logic, but for stateful logic. Good candidates for extraction: data fetching, debouncing, window dimensions, local storage sync, keyboard shortcuts, online/offline detection, previous value tracking.

When to Extract a Custom Hook

  • Reuse: 2+ components need the same stateful logic
  • Complexity: The logic deserves its own name and file
  • Testability: You want to unit-test the logic independently
  • Readability: Components become cleaner when logic is extracted

Common Custom Hooks

  • useDebounce(value, ms) — delay value updates
  • useLocalStorage(key, init) — persist state across sessions
  • useWindowSize() — track viewport dimensions
  • useOnClickOutside(ref, handler) — detect outside clicks
  • usePrevious(value) — track previous render's value
  • useMediaQuery(query) — responsive breakpoints in JS
  • useIntersectionObserver(ref) — detect element visibility

function useLocalStorage(key, initialValue) {
  const [stored, setStored] = useState(() => {
    try {
      const item = localStorage.getItem(key);
      return item ? JSON.parse(item) : initialValue;
    } catch {
      return initialValue;
    }
  });

  const setValue = (value) => {
    try {
      const toStore = value instanceof Function
        ? value(stored) : value;
      setStored(toStore);
      localStorage.setItem(key, JSON.stringify(toStore));
    } catch (err) {
      console.error(err);
    }
  };

  return [stored, setValue];
}

Definition — Memoization in React
Memoization is an optimization technique that caches the result of an expensive operation and returns the cached result when the same inputs occur again — instead of recomputing. React provides three memoization tools: React.memo for components (skip re-renders), useMemo for computed values (skip recalculations), and useCallback for function references (skip reference changes). All three use shallow equality (via Object.is) to compare previous and current inputs.
Golden Rule: Don't memoize by default. Memoization has a real cost — memory to store the cache, and time to run the comparison on every render. Profile with React DevTools first. Only memoize when you've confirmed a real performance bottleneck.
🧠

React.memo — Skip Component Re-renders

Wraps a component in a memoization layer. Before re-rendering, React shallowly compares the new props to the previous props. If all props are equal (Object.is), it reuses the last rendered output and skips the render entirely. A custom comparator function can be passed as the second argument for deep or selective comparisons.

// Expensive list item — re-renders only when needed
const ProductCard = React.memo(
  function ProductCard({ product, onAddToCart }) {
    return (
      <div>
        <h3>{product.name}</h3>
        <button onClick={() => onAddToCart(product.id)}>
          Add to Cart
        </button>
      </div>
    );
  }
);
// ⚠️  Only works if onAddToCart is also stable!
// Wrap with useCallback in the parent.
🔢

useMemo — Cache Computed Values

Caches the result of a computation. Re-computes only when the listed dependencies change. Use for expensive calculations: complex sorting, filtering large datasets, building derived data structures, or any CPU-heavy transformation. Do not use for simple calculations — the overhead of the memo itself would outweigh the benefit.

// Sort 10,000 products — expensive if done every render
const sortedProducts = useMemo(() => {
  console.log('Sorting...'); // runs rarely
  return [...products]
    .filter(p => p.inStock)
    .sort((a, b) => a.price - b.price);
}, [products]); // recomputes only when products changes

// ❌ DON'T memo simple calculations
const double = useMemo(() => n * 2, [n]); // pointless overhead
const double = n * 2; // ✅ just compute it inline
📎

useCallback — Stable Function References

Caches a function reference. Without it, a new function object is created on every render, causing any React.memo child that receives it as a prop to see a "changed" prop and re-render unnecessarily. Use when passing callbacks to memoized children, or when a function is listed as a useEffect dependency.

// Parent creates a stable handleDelete reference
const handleDelete = useCallback(
  (id) => {
    setProducts(prev => prev.filter(p => p.id !== id));
  },
  [] // no deps → same reference forever
);

// ProductCard.memo will skip re-renders now
// because onDelete reference is stable
{products.map(p =>
  <ProductCard key={p.id} product={p}
               onDelete={handleDelete} />
)}
🔗

The Memoization Chain

These three tools must be used together to be effective. Using React.memo without useCallback on the passed callback is useless — the callback is a new reference every render. The full chain: React.memo on the child + useCallback on every callback prop + useMemo on any expensive object passed as prop.

Ask during interview: "Before adding these, let me check React DevTools Profiler to confirm this component is actually re-rendering too often and causing a real performance problem." This signals engineering maturity.

Model Interview Answer — State Architecture
I categorize state into: server state (data from APIs — use TanStack Query for caching/refetching), global client state (auth, cart, theme — Context for simple cases, Zustand for anything that updates frequently), and local UI state (modal open, form input — plain useState in the component). Definition — Code Splitting
Code splitting is the practice of dividing your JavaScript bundle into smaller chunks that are loaded on demand, rather than shipping everything upfront. React.lazy + Suspense enables component-level splitting: a component's code is not included in the initial bundle and is fetched from the server only when the component is actually rendered. This dramatically reduces Time-to-Interactive for large applications.
Definition — List Virtualization
Virtualization (or windowing) is a rendering optimization for large lists where only the items currently visible in the viewport are rendered as real DOM nodes. As the user scrolls, off-screen items are recycled. A list of 10,000 items with virtualization renders ~15 DOM nodes instead of 10,000, reducing memory usage, paint time, and scroll jank dramatically. Libraries: react-window, react-virtual, react-virtuoso.

Higher-Order Components (HOC)

A function that takes a component and returns a new enhanced component, adding props or behaviour. Used for cross-cutting concerns: logging, auth guards, analytics, feature flags. Largely replaced by hooks but HOCs are still the only option when you need to wrap components at the meta/library level (e.g. Redux connect).

const AuthPage = withAuth(DashboardPage);
const TrackedBtn = withAnalytics(Button);
🚦

Error Boundaries

Class components (or the Suspense+ErrorBoundary pattern) that catch JavaScript errors anywhere in their child component tree, log them, and display a fallback UI instead of crashing the whole app. componentDidCatch + getDerivedStateFromError are the class lifecycle methods involved. In React 19, use the new useErrorBoundary hook.

<ErrorBoundary fallback={<Error />}>
  <WidgetThatMightCrash />
</ErrorBoundary>

Debounced Product Search

One of the most common coding round tasks. The examiner is testing whether you understand: (1) why debouncing is needed, (2) how to implement it without a library, (3) how to cancel stale requests, and (4) how to manage all three UI states cleanly.

Why Debounce?
Without debouncing, every keystroke triggers an API call. Typing "react" fires 5 calls in ~200ms. The last call to resolve might not be the last call sent (race condition). Debouncing waits until the user pauses typing for N milliseconds before firing — reducing API calls and eliminating race conditions.

Examiner Checklist

  • ✅ Custom useDebounce hook — not just inline setTimeout
  • ✅ AbortController to cancel in-flight requests on unmount/change
  • ✅ Three states: loading, error, data (empty is handled)
  • ✅ key prop on rendered list items
  • ✅ res.ok check — fetch doesn't throw on 404/500
  • ✅ Input has a label for accessibility
  • ✅ Ignore AbortError in catch block
DEBOUNCED SEARCH — COMPLETE SOLUTION
// 1. Reusable debounce hook
function useDebounce(value, delay = 400) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(timer); // cancel on re-type
  }, [value, delay]);
  return debounced;
}

// 2. Main search component
function ProductSearch() {
  const [query,   setQuery]   = useState('');
  const [results, setResults] = useState([]);
  const [status,  setStatus]  = useState('idle');
  const debouncedQuery = useDebounce(query, 400);

  useEffect(() => {
    if (!debouncedQuery.trim()) {
      setResults([]); setStatus('idle'); return;
    }

    const ctrl = new AbortController();
    setStatus('loading');

    (async () => {
      try {
        const res = await fetch(
          `/api/products?q=${encodeURIComponent(debouncedQuery)}`,
          { signal: ctrl.signal }
        );
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const data = await res.json();
        setResults(data);
        setStatus('success');
      } catch (err) {
        if (err.name !== 'AbortError') setStatus('error');
      }
    })();
    return () => ctrl.abort();
  }, [debouncedQuery]);

  return (
    <div>
      <label htmlFor="search">Search Products</label>
      <input id="search" value={query}
             onChange={e => setQuery(e.target.value)}
             placeholder="Type to search..." />

      {status === 'loading' && <p>Searching...</p>}
      {status === 'error'   && <p>Something went wrong.</p>}
      {status === 'success' && !results.length && (
        <p>No products found for "{debouncedQuery}"</p>
      )}
      <ul>
        {results.map(p => (
          <li key={p.id}>{p.name} — ${p.price}</li>
        ))}
      </ul>
    </div>
  );
}

Multi-Step Form

Tests your ability to manage complex state across multiple views, validate per-step before advancing, and present a clean review before submission.

Key Design Decisions
Use useReducer for multi-step form state because: (1) all fields + step number live in one place; (2) named action types (NEXT, PREV, UPDATE, RESET) self-document the transitions; (3) the reducer is a pure function — easy to unit test.

Examiner Checklist

  • ✅ useReducer for multi-field state
  • ✅ Per-step validation before advancing
  • ✅ Disable Next button when validation fails
  • ✅ Progress indicator (step N of M)
  • ✅ Review step shows all collected data
  • ✅ Loading state during async submit
  • ✅ Error handling on submit failure
  • ✅ RESET after success
Step 1 — Personal Info
name (required, min 2 chars), email (must include @), phone (optional)
Step 2 — Account Setup
username (min 3 chars, alphanumeric), password (min 8, has uppercase + number)
Step 3 — Review & Submit
Show summary, POST to API, handle success/error
MULTI-STEP FORM — COMPLETE SOLUTION
const STEPS = ['Personal', 'Account', 'Review'];

const init = { step:0, name:'', email:'',
               username:'', password:'' };

function formReducer(state, action) {
  switch (action.type) {
    case 'UPDATE':
      return { ...state, [action.field]: action.value };
    case 'NEXT': return { ...state, step: state.step + 1 };
    case 'PREV': return { ...state, step: state.step - 1 };
    case 'RESET': return init;
    default: return state;
  }
}

function validate(state) {
  if (state.step === 0)
    return state.name.length >= 2 && state.email.includes('@');
  if (state.step === 1)
    return state.username.length >= 3 && state.password.length >= 8;
  return true;
}

function MultiStepForm() {
  const [form, dispatch] = useReducer(formReducer, init);
  const [submitting, setSubmitting] = useState(false);
  const [error, setError] = useState(null);

  const update = (field) => (e) =>
    dispatch({ type: 'UPDATE', field, value: e.target.value });

  const submit = async () => {
    setSubmitting(true); setError(null);
    try {
      await registerUser(form);
      dispatch({ type: 'RESET' }); // success
    } catch (err) { setError(err.message); }
    finally { setSubmitting(false); }
  };

  return (
    <div>
      {/* Progress */}
      <p>Step {form.step + 1} of {STEPS.length}: {STEPS[form.step]}</p>

      {form.step === 0 && (
        <>
          <input value={form.name}  onChange={update('name')}  placeholder="Full Name" />
          <input value={form.email} onChange={update('email')} placeholder="Email" />
        </>
      )}
      {form.step === 1 && (
        <>
          <input value={form.username} onChange={update('username')} placeholder="Username" />
          <input type="password" value={form.password}
                 onChange={update('password')} placeholder="Password" />
        </>
      )}
      {form.step === 2 && (
        <div><p>{form.name} | {form.email} | @{form.username}</p></div>
      )}

      {error && <p style={{color:'red'}}>{error}</p>}

      <div>
        {form.step > 0 && (
          <button onClick={() => dispatch({type:'PREV'})}>Back</button>
        )}
        {form.step < STEPS.length - 1 ? (
          <button disabled={!validate(form)}
                  onClick={() => dispatch({type:'NEXT'})}>
            Next
          </button>
        ) : (
          <button disabled={submitting} onClick={submit}>
            {submitting ? 'Submitting...' : 'Submit'}
          </button>
        )}
      </div>
    </div>
  );
}

Pagination with useMemo

A staple coding round question. Shows your understanding of slice math, derived state, memoization, and edge cases like empty results or a single page.

Key Formulas
totalPages = Math.ceil(data.length / pageSize)
startIndex = (currentPage - 1) * pageSize
pageData = data.slice(startIndex, startIndex + pageSize)

Examiner Checklist

  • ✅ Reset to page 1 when data/filter changes
  • ✅ Disable Prev on page 1, Next on last page
  • ✅ Handle empty data gracefully
  • ✅ useMemo to avoid slicing on every render
  • ✅ Show "Page X of Y" / "No results" states
  • ✅ Accessible prev/next button labels
Common mistake: Not resetting page to 1 when the dataset changes (e.g. after a search). If you're on page 5 and apply a filter that returns 6 results, page 5 is now out of bounds.
PAGINATION HOOK + COMPONENT
function usePagination(data, pageSize = 10) {
  const [page, setPage] = useState(1);

  // Reset to page 1 whenever the data array changes
  useEffect(() => setPage(1), [data]);

  const totalPages = Math.max(1, Math.ceil(data.length / pageSize));

  // Only re-slice when data, page, or pageSize changes
  const pageData = useMemo(() => {
    const start = (page - 1) * pageSize;
    return data.slice(start, start + pageSize);
  }, [data, page, pageSize]);

  return {
    pageData, page, totalPages,
    prevPage:   () => setPage(p => Math.max(1, p - 1)),
    nextPage:   () => setPage(p => Math.min(totalPages, p + 1)),
    goToPage:   (n) => setPage(Math.max(1, Math.min(n, totalPages))),
    hasPrev:    page > 1,
    hasNext:    page < totalPages,
  };
}

// Usage with search + pagination combined
function ProductList({ allProducts }) {
  const [search, setSearch] = useState('');

  // Derived state — filter before paginating
  const filtered = useMemo(() =>
    allProducts.filter(p =>
      p.name.toLowerCase().includes(search.toLowerCase())
    ),
    [allProducts, search]
  );

  const { pageData, page, totalPages,
          prevPage, nextPage, hasPrev, hasNext }
    = usePagination(filtered, 12);
  // Changing search resets page to 1 automatically!

  return (
    <div>
      <input value={search} onChange={e => setSearch(e.target.value)}
             placeholder="Filter products..." />

      {pageData.length === 0
        ? <p>No results found.</p>
        : <ul>{pageData.map(p =>
            <li key={p.id}>{p.name}</li>
          )}</ul>
      }

      <nav aria-label="Pagination">
        <button onClick={prevPage} disabled={!hasPrev}
                aria-label="Previous page">←</button>
        <span>{page} / {totalPages}</span>
        <button onClick={nextPage} disabled={!hasNext}
                aria-label="Next page">→</button>
      </nav>
    </div>
  );
}
Quick Quiz
Test Your
Knowledge

Real interview questions. Click any option to see the answer and explanation.

1. What will happen if you call useState inside an if statement?
React tracks hooks by their call order, stored as a linked list per component instance. If a hook is skipped (condition is false), all subsequent hooks shift position, causing each subsequent hook to read the wrong state cell. React throws an invariant violation error to prevent this. This is why the "Rules of Hooks" lint rule exists — ESLint's eslint-plugin-react-hooks catches this statically.
2. A parent renders. It passes an inline function () => handleDelete(id) as a prop to a React.memo child. Does the child re-render?
React.memo uses Object.is() for prop comparison — which for functions checks reference equality. Every parent render creates a new function object in memory. () => handleDelete(id) on render 1 and () => handleDelete(id) on render 2 are two different objects. React.memo sees "prop changed" and re-renders the child, negating all memoization benefit. Fix: wrap the callback in useCallback in the parent.
3. useEffect runs after every render. You want it to run only on mount. What do you do?
The dependency array tells React when to re-run the effect. With an empty array [], React compares no dependencies between renders — there's never a "change" to trigger a re-run, so the effect runs only once after the initial mount. The cleanup function (if returned) still runs on unmount. Note: using null causes the same behaviour as no array (every render). useLayoutEffect also respects the dependency array identically — it just fires at a different time.
4. What is the difference between useMemo and useCallback?
useMemo(() => compute(), [deps]) — calls the function and caches its return value. Every time deps change, it recomputes. Used for expensive calculations. useCallback(() => fn, [deps]) — caches the function reference itself, not its return value. Equivalent to useMemo(() => () => fn, [deps]). Used to give memoized children stable callback references. In fact, useCallback(fn, deps) is exactly useMemo(() => fn, deps).
5. Why should you never use array index as the key prop for a dynamic list?
React's reconciler uses the key to match old and new virtual DOM nodes. With index keys, if you remove item at index 0, every remaining item's index shifts by -1. React thinks "index 0 still exists" — it reuses the old DOM node and just updates its props, potentially applying one item's state to another. Classic bug: controlled inputs showing values from the wrong item after deletion. Always use stable, unique IDs from your data. Only use index as key for static lists that never change order or length.
6. What is a "stale closure" in React and how do you fix it?
A stale closure happens because the effect callback is a closure that captured the state variable at creation time. With an empty [], the callback is created once on mount and never re-created — so it forever sees the initial value. Fixes: (1) Add the variable to the dependency array — React will recreate the closure with the fresh value. (2) Use the functional updater: setState(prev => prev + 1) — this doesn't read the closure value; it reads from React's internal store. (3) Use useRef to store a mutable latest-value container that doesn't need to be in deps.
7. When should you use useReducer instead of useState?
The decision is about complexity and clarity. useState is perfect for 1-3 independent values. Switch to useReducer when: (1) multiple fields need to update atomically (e.g. a form with step + fields + errors); (2) state transitions have domain-meaningful names (ADD_TO_CART, CHECKOUT, CLEAR) that serve as documentation; (3) the next state depends on the current state in complex conditional logic; or (4) you want the state logic to be testable as a pure function completely independent of React.
